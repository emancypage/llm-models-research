# OBLITERATUS issues and possible improvements (working log)

OBLITERATUS `7678d84196fe6c348dfd01078bbfb50857463647`. Started on 22 November 2026 and updated during the study. Each entry gives the symptom, the models affected so far, the workaround and a proposal.

| # | Symptom | Models | Workaround | Proposal |
| --- | --- | --- | --- | --- |
| 1 | `recovery-distill` writes `take` equal to the requested prompt count. When the refusal filter (`drop`) removes rows, `recovery-data` rejects the corpus as incomplete. | Q1 (study 1) | A copy of the manifest with `take` equal to the rows kept by `accepts_messages` (`fix_take.py`). | Write the kept count, or let `recovery-data` accept counts reduced by the declared refusal policy. |
| 2 | `verify-edit` drops the per-prompt refusal and `invalid` flags before it writes the report (`runner._strip`). Refusal changes cannot be tested in pairs. | all | A wrapper that replaces `_strip` and keeps the flags (`verify_flags.py`). It reproduces the tool's counts exactly. | An option that keeps per-prompt flags (no prompt text). |
| 3 | `recovery-distill` rejects every prompt that is in `BUILTIN_HARMFUL`. All harmful prompts of the `qwen38-v1` protocol come from that set, so a `keep` or `require` corpus cannot use the protocol's `train` split. The same check runs again on every corpus load (`recovery-data`, recipe build). | all (RK) | A wrapper (`narrow_disjoint.py`) that limits the check to the `tune` and `final_test` partitions in the RK distill, corpus and build processes; its record names the narrower battery. | Document the intended source of harmful prompts for `keep`/`require`, or ship a separate harmful set that is disjoint from the evaluation battery. |
| 4 | In NVIDIA container images `peft` imports `transformer_engine`, which needs `libcuda` even for CPU-only repair training. | all | Run CPU builds with the GPU attached to the container. | Import `transformer_engine` lazily, or document the requirement. |
| 5 | A `recipe search` profile without `kl_policy` makes KL a required gate. In study 1 no candidate won, not even the accepted recipe. | Q1 (study 1) | Set `"kl_policy": "advisory"` at the top level of the profile. | Warn when a search profile leaves KL as a required gate while the accepted profile treats it as advisory. |
| 6 | The `adapter.lora_repair` recipe step runs only on CPU in float32 (71 min for Q1 in study 1). | Q1 | Standalone `recover` on CUDA in bf16 (arm RG) is tested as an alternative. | Allow CUDA bf16 in the recipe step, as `recover` does. |
| 7 | The projection inside the v2 recipe (CPU, float32) differs from the accepted GPU edit by more than bf16 rounding. The cause is not isolated. | Q1 (study 1) | P from the same run is the reference for R. | Document the expected difference between devices and precisions. |
| 8 | Repair training requires an in-vocabulary pad token (`recover.py`, `encode_examples`). Llama 3 tokenizers have none, so `lora_repair` and `recover` cannot run on stock Llama 3 checkpoints. | L3, L8 | A stock copy with `pad_token: <\|finetune_right_pad_id\|>` (id 128004) in `tokenizer_config.json`, used for every Llama arm. | Fall back to a reserved in-vocabulary pad token, or document the required tokenizer change. |
| 9 | `recipe search` looks up a Hub `model_id` with `snapshot_download(local_files_only=True)` (`recipes/search.py`, `_stock_checkpoint`). With `huggingface_hub` 1.24 this fails with `IncompleteSnapshotError` when the cache holds only the files a model needs (weights, config, tokenizer) and lacks e.g. `LICENSE`, `README.md`, `.gitattributes` or `merges.txt`. Loading the same snapshot as a directory works. | Q3 | The grid names the cached snapshot directory as `stock.model_id` (same weights, revision kept in the grid). | Resolve the snapshot directory for a pinned revision without requiring every repository file, or report which files are missing and that a local directory is accepted. |
| 10 | When a `recipe search` candidate fails for an infrastructure reason (here: checkpoint export ran out of container memory, `NativeExportCapacityError`), the search still publishes a winner from the remaining candidates and exits 0. `selection.json` gives only "obliterate failed (exit 1)"; the cause is in the candidate's `obliterate.log`. The winner can change once the failed candidate runs (Q3: 18–28 among 4, then 13–23 with 2 directions among 5). | Q3 | Resume the search with a larger memory limit; the tool reruns only failed candidates. | Do not publish a winner while a candidate failed, or mark the selection incomplete and exit non-zero; copy the error class into `selection.json`. |
| 11 | On models under 2 billion parameters, with hidden size under 2048 or with at most 16 layers, the projection caps `n_directions` at 2 when `small_model_safeguards` is on (the preset default). A v2 recipe that does not set the flag stops with "projection would adapt the edit without explicit small_model_safeguards". The message does not name the cap (here: 4 directions to 2), and it comes after the probe and direction extraction (5.5 min for Q1 on CPU). | Q1 | Set `small_model_safeguards` explicitly in the projection overrides (`false` keeps the requested directions). | Check the cap before the probe, and name the cap and the values in the error. |
| 12 | The family recipe `llama3-instruct-family-e03` matches `meta-llama/Llama-3*-Instruct`, which includes members with tied embeddings (Llama 3.2 1B and 3B), but it does not set `lm_head` or `allow_tied_head_edit`. On such a member the build stops with "projection of tied lm_head requires allow_tied_head_edit: true or lm_head: skip", and only after the probe and direction extraction (12 min for L3 on CPU). | L3 | Set `allow_tied_head_edit: true` in the projection step (the family default edits the head on untied members). | Set the head control in family recipes whose pattern matches tied members, and check for a tied head before the probe. |
